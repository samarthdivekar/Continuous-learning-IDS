10 · Every page and every feature of the console

The console is a website that runs in the browser at http://localhost:8080. It has eight pages in two groups: Operate (what a security team uses day to day) and Evaluate (the evidence that the model works). Every number on screen is read from a result file or from the live model; nothing is typed in by hand. Screenshots were taken from the running system with the model service up, in the dark theme at 1440×900.

10.2 Overview: "does it work?" in one screen

  • In plain words: a sentence generated from the result files, e.g. "the model learned 7 attack types one after another… after the last one it still catches 100 % of the first attack type, while a normally retrained model catches 0 %. It wrongly flags about 66 of every 100,000 normal flows."
  • Four KPI tiles: our macro-F1 (0.964 ± 0.020 over 3 seeds, versus 0.928 for the per-flow FFNN), retention of the first attack (100 %, versus 0 % for naive retraining), false-positive rate (0.07 %), drift-triggered retrains (16, where the oracle needed 6).
  • The core claim, measured: per model, does it adapt (recall on each new category) and does it remember (recall on the first category at the end)? A tick appears at 80 % or more; the rule is written on the panel.
  • Attack timeline: attack and benign test flows per task, in capture order.
  • System architecture diagram and a Dataset panel (flows, window graphs, features, tasks).

Example use: an examiner asks "does it forget?". Open Overview, point at the Retention tile (100 %) and the red 0 % for naive retraining underneath it.

10.3 Incident queue: what an analyst works through

Why it exists: analysts cannot read thousands of flow alerts. This page groups them into incidents, explains each one, proposes a response and records the human decision.

What to reviewOne window (pick a traffic window) or Recent (scan the last 10/20/50 windows and rank incidents across them, like a shift's queue).
DetectorWhich model scores the traffic: ours, the per-flow FFNN, or naive retraining.

10.6 Classify: run the models on demand

  • A held-out window: choose a test window and press Classify window. Each loaded model labels all 5,000 flows; the chart compares counts per category with the ground truth, and the table shows how many flows each flagged. In this example our model flags exactly the 258 attack flows.
  • Your own flows: drop or choose a CSV with src_ip, dst_ip and all 83 trained features. The panel previews rows and columns before sending. A file missing any feature is rejected with the missing names listed, because a verdict computed on made-up zeros would look authoritative and mean nothing. Limits: 5 MB, 5,000 flows per request. For 50 flows or fewer a per-flow verdict table with confidences appears.

10.7 Models: the evidence about quality

  • Metric over tasks (choose the metric): our model stays near the top; naive retraining and XGBoost fall as attacks are added.
  • Per-category recall matrix: rows are "after task i", columns are attack types; forgetting shows as a column going dark.
  • Forgetting (BWT) bar chart, and a confusion matrix for any model after any task.
  • Compare models on adds every ablation (FFNN, replay-only, EWC-only, joint upper bounds).
  • Unseen attacks: each model trained without one category, then tested on it. Bars show the share detected. When a more than one seed exists the table adds Seeds and Per seed columns (CSE-CIC-IDS2018 BruteForce reads 99.7 % / 0.07 % / 100 % over three seeds; DoS 98.6 % on all three).
  • IP leakage test: the same model scored normally, with host identities shuffled (permute: must not change, and does not), and with every flow's source randomised (random_src: the attacker stops being one hub; our model falls from 0.952 to 0.431 in all three seeds, the per-flow model is unaffected). This is the project's most important honest limitation.

10.8 Adaptation & trust

  • Retrains vs final macro-F1: bars are retrain cycles, the line is final quality, for ADWIN, a fixed schedule, the oracle and never adapting.
  • Policy scoreboard: flags, retrains, macro-F1 and retention per model and policy, labelled with how many seeds are summarised.
  • Error timeline: per-window error with drift flags and adaptations, for the selected run.
  1. Does it notice an attack it was never taught? AUROC per unseen category for three novelty scores (choose energy, max softmax or prototype distance), plus clustering of novel flows into candidate new categories.
  2. Does it know when not to decide? Conformal abstention: false alarms before and after, share handed to an analyst.
  3. Will analysts drown in alerts? Flow alerts vs incidents at different false-alarm budgets.
  4. Can it adapt safely without labelling everything? All labels vs 100 labels per update (half least certain, half random) vs the safety gate that rolls back a bad update. Labelled single run, indicative only.

10.9 Reproducibility: check, don't trust

  • Reproduce everything: the single command (python -m experiments.reproduce_all --dataset cicids2017) with a Copy button.
  • EWC λ sweep: validation macro-F1 for each penalty strength (log axis), the chosen value marked.
  • Training-budget tuning: the settings tried on the validation split and the one selected.
  • Run metadata: timestamp, seed, GPU, Python and package versions of the run that produced the numbers.
  • EWC stability: a check that the penalty never became large enough to destabilise training.

11.3 How it was built, step by step

  1. Data pipeline on the corrected datasets, with tests on synthetic data.
  2. The graph model, the per-flow model and the tree baseline, then EWC and replay, then the task-sequence experiment.
  3. ADWIN drift detection and the streaming experiment.
  4. Hyper-parameters tuned on the validation split only (epochs, class balancing, EWC λ and γ).
  5. The API, database and console; then the product layer (incidents, explanations, abstention, novelty, dry-run response).
  6. A results-integrity review that found and fixed several defects (for example a label-dependent sampling step that would have leaked labels into the graphs); affected experiments were re-run.
  7. A senior review called the project "over-built and under-proven". The response: a temporal split, five seeds, paired statistics, a serving benchmark, calibration, a replay-budget sweep, a mixed-attack stream, extra seeds, removal of weak features (free-form CSV paste, a one-seed table, the Docker setup), the console redesign and a browser smoke test.

11.4 Is there an API key?

  • No external API keys are used anywhere. No cloud service, no OpenAI/Claude or other language model, no paid API. Explanations are generated by rules in Python; everything runs locally.
  • The project's own API can require a key. Set the environment variable GNNIDS_API_KEY before starting the stack. Then every endpoint except /health requires the header X-API-Key. The console asks for the key once, stores it in the browser and sends it only in that header (never in a web address). By default no key is set, which is fine on a single laptop and is listed as a limitation for any real deployment.
  • Other protections: strict Content-Security-Policy on the console, checkpoints loaded in PyTorch's safe weights-only mode where possible, and response actions that are never executed.

13 · Limitations and future work

Limitations (say these before an examiner does)

  • Topology dependence. When attack traffic comes from many random sources the graph model collapses (0.952 → 0.431, 3 seeds). Training with randomised sources recovers 0.914 but costs in-distribution accuracy (appendix in the README).
  • Lab data. Both datasets are laboratory captures from 2017 and 2018 with attacks in clean blocks.
  • Few seeds. Three to five seeds give indicative, not conclusive, statistics. Some product results are one run.
  • Labels are needed for drift. ADWIN watches the labelled error; a label-free trigger missed most drift.
  • Seed instability. On 2018 the identical configuration scored 0.855, 0.948 and 0.945 in three trainings; unseen BruteForce flipped between seeds.
  • Not a product. No TLS, no roles, no rate limiting; flows stored in clear text; CSV input only.
  • Windows Smart App Control blocked PyTorch for part of the project; it was turned off and the remaining experiments are being run (status in the README).

Future work

  • Validate on newer and real traffic; ingest Zeek or Suricata output directly.
  • Reduce topology dependence without losing accuracy (better augmentation, host-agnostic features).
  • Learn from fewer labels; test label-free drift signals that work.
  • Authentication, TLS and roles for a real deployment.

14 · Things you might have missed

14.1 Likely viva questions, with short answers

What is new here?The combination, evaluated honestly: a graph detector that learns attacks continually, decides when to retrain, detects some never-seen attacks, and reduces analyst workload, with a temporal split, seeds and statistics. Not a new algorithm.
Why a graph instead of Random Forest?Attacks have shapes between hosts that per-flow models cannot see; it detects never-seen attacks far better (>80 % in 6 of 12 tests vs ≤0.07 %), and it can learn new attacks without retraining on everything (section 7).
Your test windows are next to your training windows. Isn't that cheating?That was the interleaved split. The temporal split tests on later traffic for every attack; it costs 0.049 macro-F1 and is reported alongside.
Is the difference statistically significant?With 3–5 seeds no Wilcoxon test can reach p < 0.05; the bootstrap intervals exclude zero, so the gain is indicative. We say exactly that.
Does EWC help?EWC alone fails. On top of replay: no detectable gain on the interleaved split; it prevented two collapses on the temporal split. Replay is the key ingredient.
Why 2017/2018 data?Sequence of many attacks over days, IP addresses kept for graphs, independently corrected releases, comparability with published work, enterprise traffic (section 8).
Could it memorise IP addresses?No: IPs are never features, and shuffling host identities changes nothing. But it does rely on attackers being few hosts.
Can it run in real time?Scoring takes 5.5 ms per 5,000 flows on a laptop GPU; flow export and graph building from raw traffic are not in that figure.
What happens if the model is wrong?It can abstain, every action is a dry run, and a safety gate can roll back a bad update.
Why does ADWIN retrain more than a schedule?Attack bursts inside a task keep raising the error until the model has adapted. It wins when attacks are mixed, not when they arrive in clean blocks.
What would you do with more time?Real traffic, less topology dependence, fewer labels, deployment security.

14.4 Glossary

FlowOne network conversation summarised by 83 numbers.
Window5,000 consecutive flows turned into one graph.
TaskA period in which a new attack type appears.
Macro-F1Detection quality averaged over all categories (1.0 is perfect).
RetentionRecall on the first attack after learning all the others.
FPRShare of normal traffic wrongly flagged.
BWTBackward transfer: how much old tasks got worse; negative is forgetting.
Catastrophic forgettingA network overwriting old knowledge when trained on new data.
EWCElastic Weight Consolidation: stiffen the weights that mattered before.
ReplayRehearse a few stored old windows while learning new ones.
ADWINAdaptive windowing drift detector.
Concept driftThe data changing after training.
Conformal predictionPrediction sets with coverage guarantees, used to abstain.
ECEExpected calibration error: gap between confidence and accuracy.
AUROCArea under the ROC curve; 0.5 is chance, 1.0 perfect separation.
Leave-one-attack-outTrain without one attack type, test on it (unseen-attack test).
Interleaved / temporal splitTest windows between training windows / strictly later in time.
SeedThe random starting point of a training run; more seeds = more trustworthy averages.
Dry runAn action that is proposed and recorded but never executed.
CEFCommon Event Format, a log line format that SIEM tools import.
