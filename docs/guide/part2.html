7 · The machine-learning model: why a graph network, and why not Random Forest

7.1 The model we use, in plain words

The deployed model is called gnn_ewc_replay: an E-GraphSAGE graph neural network trained with EWC and replay. Here is what happens to one flow, step by step:

  1. Build the graph. The 5,000 flows of a window become a graph. Each computer is a node; each flow is an edge carrying its 83 numbers (scaled so that big and small numbers are comparable). Each node also gets simple structural numbers: how many flows it sends and receives.
  2. Look around (two hops). For each computer the model gathers a summary of the flows going out of it and the flows coming into it, separately (direction matters: a scanner sends, a victim receives). It does this twice, so a computer's summary also reflects its neighbours' neighbours.
  3. Decide per flow. For each flow, the summaries of its two endpoints are joined with the flow's own numbers (the "edge skip", so the flow itself is never drowned out), and a small classifier outputs a probability for benign and for each attack type.
Hidden size / layers64 / 2 (two hops of neighbourhood)
Parameters69,128 (the per-flow FFNN ablation has 55,432)
Training per task10 epochs, Adam, learning rate 0.001, class weights for rare attacks (chosen on the validation split, never on test)
EWCλ = 10, γ = 0.9 (chosen by a validation sweep over λ and γ)
Replayup to 10 stored windows per attack category, 2 replayed at every training step

7.3 Why not Random Forest (or any per-flow tree model)?

You mentioned an early Random Forest version that was dropped. It is not in this repository's history, which starts on 17 September 2026, so this guide explains the decision using the tree-ensemble baseline the repository does contain: XGBoost. Random Forest and XGBoost are close relatives: both are many decision trees voting, and both judge each flow on its own.

Random Forest is a good classifier and a sensible first attempt. It was replaced because the product needs four things a per-flow tree model cannot provide:

NeedRandom Forest / XGBoostGraph neural network with continual learning
See relationships between computers (scans fan out, floods fan in)Judges one row at a time; "this host talked to 996 ports" is invisible unless you hand-craft extra features.Reads the neighbourhood directly from the graph.
Catch attacks never trained onOur XGBoost baseline caught 0 % of five of the six never-seen 2018 attacks (90.1 % on DoS only); the per-flow neural network caught at most 0.07 % on all of them.More than 80 % in 6 of 12 held-out tests.
Learn new attacks over time without starting from scratchTrees are rebuilt from scratch; to keep old knowledge you must keep and retrain on all old data. A tree model trained once (our XGBoost static) ends at 0.231 macro-F1 because it never learns the later attacks.Updates on the new task, rehearsing only a small replay buffer, and keeps 99.8–100 % retention.
Say "I'm not sure" and "this is new"Tree vote fractions are poorly calibrated probabilities; no learned embedding for distance-based novelty.Softmax probabilities support conformal abstention, and the hidden layer gives embeddings for novelty and drift scores.

Where Random Forest would be the right choice: a fixed set of known attacks, no need to learn over time, and a need for very fast CPU-only training with feature importances out of the box. That is not this product's situation.

7.4 How the model choice benefits the product

  • Incidents come naturally. Because the model already thinks in hosts and connections, grouping flagged flows into attacker/victim incidents uses the same graph.
  • Better explanations. The explanation can say "80 % of the evidence came from neighbouring flows", which tells an analyst the graph context mattered (see the incident detail screenshot).
  • Fewer missed new attacks. Structural patterns transfer to attacks the model never saw, at least for some of them.
  • Cheap to keep current. Each update trains on the new traffic plus a small buffer, in seconds per task on a laptop GPU, instead of retraining on everything.

8.2 Why these two, and not more recent ones?

Newer intrusion datasets exist (for example CIC-DDoS2019, BoT-IoT, TON_IoT and CIC-IoT2023). These two were chosen because the project needs a very specific combination, and they are the best-documented datasets that have it:

  1. Many different attack types arriving one after another, with timestamps. Continual learning needs a natural sequence of new attacks. Both datasets recorded different attacks on different days, so the capture schedule gives a realistic order of tasks. Datasets built around one attack family (such as a DDoS-only set) cannot provide that.
  2. Source and destination addresses kept. A graph needs to know who talked to whom. Some re-released datasets anonymise or drop addresses, which makes graph building impossible.
  3. Corrected versions exist. Researchers found and fixed thousands of labelling and flow errors in exactly these two datasets (papers 02 and 03). A detector evaluated on wrong labels gives wrong numbers (paper 04). Very few newer datasets have had this level of independent checking.
  4. Comparability. They are the most-used enterprise intrusion benchmarks, including by the graph and continual-learning papers this project builds on (12, 13, 26), so the results can be placed next to published work.
  5. Enterprise rather than IoT traffic. The target user is an organisation's security team. Many newer datasets focus on IoT devices, a different traffic profile.

The honest downside: 2017 and 2018 traffic is old, and it is laboratory traffic with attacks in clean blocks. The project tests one consequence of that directly (the mixed-attack stream, section 12) and lists validation on newer and real traffic as future work.

8.3 Why two datasets and not one?

Because one dataset can fool you. A result that holds on one network might be an accident of that network's particular hosts, timings or labelling. The second dataset is a different network (bigger, cloud-hosted, a different attack order) measured with the same features, so the same model can be tested on both. That is replication, and it changed conclusions:

  • EWC alone looked fine in 2017 binary mode but failed in the one 2018 binary run (one seed, since withdrawn), and it fails in multiclass on both datasets, which is why the project concludes that replay, not EWC, is what prevents forgetting.
  • The drift detector over-triggered on 2017; on 2018 (three seeds) it used about half the retrains of a fixed schedule (23 vs 48) but only tied it on quality (0.836 vs 0.828), winning on one seed and losing on another.
  • The graph's advantage on attacks it has seen is clear on 2017 but unstable on 2018, where the same configuration scored 0.855 in one training and 0.945 in another.
  • The strongest graph result, detection of never-seen attacks, is strongest on 2018.

8.4 How the data become tasks and test sets

Flows are sorted by time and cut into windows of 5,000. Each window belongs to the attack task during which it was captured. Each task's windows are split into training, validation and test. Two ways of splitting are reported:

Interleaved tests sit minutes away from training windows of the same attack session, which is optimistic. Temporal tests are always later in time, which is realistic.

A plain time split leaves some attacks with nothing to test on (WebAttack and Botnet would get 0 test attack flows, DoS only 11), because those attacks sit at one end of their task. So the project uses a per-attack temporal split: the windows carrying the new attack and the other windows are each split 70/10/20 in time. Every attack is then tested on its own latest traffic. This cost our model 0.049 macro-F1 (0.964 → 0.915), which is the honest price of a realistic test.

9 · How the product works, end to end

9.1 The five layers

9.2 Following one window through the system

  1. Ingestion reads the corrected CSV files, renames columns to a standard form, fixes infinite or missing values, relabels "attempted" attacks (no malicious payload) as benign as the dataset authors advise, and assigns each flow to its attack task by time.
  2. Preprocessing applies a log transform and scaling learned on training data only, clips extreme values, and cuts the stream into windows of 5,000 flows.
  3. Graph building turns each window into a graph (hosts → nodes, flows → edges) and caches it on disk, so later steps never repeat this work.
  4. Training (offline, experiments/run_continual.py) learns the tasks in order and saves a checkpoint of every model after every task.
  5. Serving: the model service loads the final checkpoints. When the console asks about window 363, it scores all 5,000 flows in about 5.5 ms on the GPU and caches the answer.
  6. Incidents: flows predicted as attacks are linked when they share hosts, giving one group per attacker/victim cluster and category. Each group gets a severity (size × confidence), a key host, an explanation and a proposed action.
  7. Human decision: the analyst approves or rejects. The decision is stored in the database with their name and a note. Nothing is executed.

9.3 Live traffic (Live sites page)

A sensor (or the cyber range) captures a few seconds of packets at a time; the pinned CICFlowMeter turns them into flows with exactly the training features; non-IP records are dropped. Each chunk is scored inside its site's last two minutes of flows, so the graph is comparable in size to the 5,000-flow training windows. Confident attack verdicts are grouped per site into incidents; flows the model cannot call attack or normal go to an Unsure list; traffic unlike anything in training is listed as Unfamiliar. An analyst's labels teach the live model, one epoch at a time on a copy, and an epoch is kept only if the model did not forget old attacks or raise false alarms (section 10.4).

9.4 The drift loop (Drift replay page)

The same steps run continuously during a replay of the recorded dataset. For each new window, each of four models predicts first. Then the true labels are revealed (the "delayed labels" an analyst would provide), the error goes to ADWIN, and if ADWIN confirms a rise in error the model adapts on the last 20 windows using its continual-learning strategy. Everything is written to the database and shown live.

9.5 Why it is split into separate services

  • The heavy model work (GPU, PyTorch) runs in its own process, so the public API stays responsive.
  • If the model service is down, the pages that read saved results still work, and a banner names the pages that need the model service.
  • The browser never talks to the model service directly. It only talks to port 8080, which is easier to secure.
